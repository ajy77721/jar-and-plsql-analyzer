### B2 ☑ Hang sites — DONE (the blind-spot list closed by B9)

**The first finding was that my own earlier "fix" never reached the running app.** The Code
Structure tree does not use `/classes/tree` unpaged — it pages 200 rows at a time via
`classTreePages`, and **the paged row carries `fields` but not `methodSummaries`**:

```
row keys: accessFlags, annotations, fieldCount, fields, fullyQualifiedName, interfaces,
          isAbstract, isEnum, isInterface, methodCount, packageName, repositoryEntityType,
          simpleName, sourceJar, stereotype, superClass
```

So the Methods section has been empty in the real app all along, and reading
`cls.methodSummaries` (PLAN-12 §4.4) only helped the unpaged fallback nobody uses.

**Measured cost of the two paths:**

| | bytes | time |
|---|---|---|
| `/classes/tree` unpaged | 11,834,160 | 2.38 s |
| — of which `methodSummaries` | 8,174,421 (65.4%) | |
| — of which `fields` | 3,551,050 (28.4%) | |
| — class-level rest (all the tree paints) | 760,701 (6.1%) | |
| paged tree, 1,623 rows (what the app uses) | 3,631,871 | 0.67 s |
| **expand one class, by name** | **2,381** | **0.28 s** |

**Fixed:**

1. `streamClassTree(parser, gen, includeMembers)` + `?members=false` on the endpoint. Omits both
   member arrays while still emitting `methodCount`/`fieldCount`, so a lean row never becomes a
   wrong number. Defaults to `true`, so every existing caller is byte-identical.
2. `codeTree.toggleClass` fetches a class's members on first expand and caches them, so methods
   render for the first time — 2.4 KB per class instead of 8.2 MB up front.

**Two bugs caught in my own fix before it shipped:**

- The presence test was `methodSummaries || methods || fields`. Paged rows *have* `fields`, so it
  would have rendered a body with no methods and never fetched — reproducing the original defect
  exactly. It now tests for methods specifically, and only fetches when `methodCount > 0`.
- The loader first used `/classes/by-index/{idx}`. That index is into **analysis.json's** class
  order, while `classIndex` is into the tree's **PACKAGE-sorted** array — they disagree, so it
  would have shown a different class's methods. It now fetches **by name** and verifies the
  returned identity before rendering.

**The remaining 74 sites turned out to be mostly false positives**, which is why they were checked
before being rewritten:

- **PL/SQL tables are already paginated.** `PA.tf` is a real table framework used at **24 call
  sites, every one at 50 rows per page** — complexity, cursors, joins, sequences, statements, table
  ops, predicates, triggers, coverage, references. The scanner flagged `plsql/js/app.js` 41 times
  mostly on things like a schema `<select>` (bounded by distinct schemas).
- **`jar/js/cross-ref.js` was already exemplary** — it caps at 200 *and* says so:
  `Showing 200 of N — type to narrow`. That wording is now the house pattern.
- **The JAR side has no `PA.tf` equivalent**, which is the real asymmetry.

**Two genuine unbounded renders found and fixed:**

| site | before | after |
|---|---|---|
| `jar/js/endpointList.js` | **no limit at all** — a card per endpoint, and the JARs this targets have thousands | caps at 200 with `Showing N of M — type to narrow, or show all`; group headers keep the TRUE count |

### B8 ☑ Runtime error: "source.fetchPage is not a function"
Reported from the running UI while B2 was in progress; the Code Structure tab failed to load.

**Not caused by the B2 changes** — `shared/page-envelope.js` defines `fetchPage` and the script tag
was intact (verified after my `index.html` edit). The trigger is a **stale cached copy**: the tag
was `page-envelope.js?v=2` and the version was never bumped when `fetchPage` was added, so a browser
holding the old file has `PA.pageSource` but gets back an object without `fetchPage`.

**The real defect is the guard**, and it is mine to own: `_fetchAllClassPages` tested that the
*factory* existed (`!window.PA || !PA.pageSource`) but never that its *product* was usable. A stale
script sails past that check and throws on the next line, killing the tab instead of falling back.

Three fixes:

1. The guard now tests `typeof source.fetchPage !== 'function'` and falls back, with a `console.warn`
   naming the likely cause rather than failing silently.
2. `?v=2` → `?v=3` on all five `index.html` files, so the stale copy is evicted.
3. The fallback is no longer expensive. `getClassTree` now requests `members=false`:

```
fallback  /classes/tree?members=false   729,546 B   0.60s   16.2x smaller
default   /classes/tree              11,834,160 B   1.85s   unchanged
counts preserved: methodCount 33,250 · fieldCount 8,577
```

#### All five datasources — done

**"This change is needed for all datasources."** There are two parser families and only Oracle used
`SqlAnalyzer`; DB2, MySQL, Postgres and SQL Server each have their own ANTLR grammar engine. Rather
than implement column analysis four more times, each dialect now contributes the one thing it
already has — the statement's original SQL — and a single shared `TableOperationEnricher` derives
the detail. One implementation, five datasources.

| piece | where |
|---|---|
| `sqlText`, `columnUsages`, `ddl` | `TableOperationInfo` (shared model) |
| statement text capture | each dialect's ANTLR visitor, from the token interval |
| the analysis | `TableOperationEnricher`, called at the end of each dialect parser's `parse()` |

Verified per dialect through the **real parsers**, not the enricher directly, so a dialect that
fails to record its SQL fails the test rather than silently producing nothing:

```
DB2        tableOps=1  withSqlText=1  withColumnDetail=1
POSTGRES   tableOps=1  withSqlText=1  withColumnDetail=1
SQLSERVER  tableOps=1  withSqlText=1  withColumnDetail=1
MySQL      SET status <- LITERAL asserted; INSERT columns asserted
Oracle     unchanged — still its own SqlAnalyzer path (asserted)
```

**Two defects caught by that per-dialect check:**

1. **DB2 and Postgres captured only `"UPDATE orders"`.** Their grammar's DML rule ends *before* the
   `SET`/`WHERE` clauses, so `ctx.getStop()` truncated the statement and produced no column detail
   at all. SQL Server's rule does span the whole statement and worked — which is exactly what made
   the truncation visible. Capture now extends to the statement terminator, tracking quotes so a
   semicolon inside a literal does not end it early.
2. **My first design decorated the factory**, which broke two existing tests asserting it returns
   the concrete `MySqlProcedureParser`/`SqlServerProcedureParser` type. That is a real contract, so
   the enrichment moved inside each parser and the factory was reverted.

**Deliberately conservative:** a statement JSqlParser cannot parse gets *no* column detail. The
table operation and every existing field are untouched. A wrong column list would appear on a
table's page as fact, which is worse than an absent one. `TableOperationEnricher.coverage()` exists
so per-dialect coverage on real sources is a measurement rather than an assumption.

#### Persistence — verified on disk, all five datasources

Fresh analyses against all five live databases (Oracle 1521, MySQL 3306, DB2 50000, SQL Server 1433,
Postgres 5432), reading `tables.json` afterwards:

| dialect | tables | with column detail | column rows |
|---|---|---|---|
| ORACLE | 42 | 30 | 60 |
| MYSQL | 232 | 161 | 421 |
| DB2 | 100 | 75 | 283 |
| POSTGRES | 114 | 97 | 236 |
| SQLSERVER | 85 | **7** | 13 |

e.g. `ERP_SALES_ORDER.STATUS usages=[SET] sources=[LITERAL]`,
`ERP_AUDIT_LOG.ENTITY usages=[INSERT] sources=[COLUMN, LITERAL, SUBQUERY]`.

**The first run of this produced zero column rows for every dialect**, while the logs said
"100% parsed". Two causes, both found only by looking at the file rather than the log:

1. **`DependencyCrawler.resolveTableSchemas` rebuilds each `TableOperationInfo` and copied only six
   fields.** The enricher filled the column detail, and this silently dropped it. It now copies
   every field — the same class of bug as a partial constructor, and invisible from the outside.
2. **Oracle never ran the enricher and never recorded statement SQL on its table operations.**
   `StoredProcedureParserFactory` returns null for Oracle, so the decoration that covered the other
   four missed it — the one datasource anyone would assume was covered first. The Oracle visitor now
   tracks the DML context and `PlSqlParserEngine` calls the same shared enricher. Note this needed a
   separate, *untruncated* text helper: the existing `getOriginalText(ctx, 200)` cuts at 200
   characters for display, and a truncated statement does not parse.

**SQL Server coverage is poor — 7 of 85 tables** against 30–161 for the others, and the enricher
logged `17/58 parsed (29.3%)` on that run. Not a crash and not wrong data: those operations simply
get no column detail. This is the signal the coverage measurement exists for, and it is where
dialect-specific handling should go next if SQL Server matters.

`ddl` is 0 across all five, which is expected here — these demo schemas contain no DDL inside
procedures. It is asserted by unit test instead.

**The house pattern is now `shared/ui-busy.js`**, loaded first on all five pages:

- `UIBusy.begin(el, label)` → a release function, or `null` if `el` is already busy. Called from
  `finally`, so **success and error settle identically** — the stated done-condition.
- `UIBusy.run(el, fn)` → the same thing wrapped around a whole call, for inline `onclick`.
- `UIBusy.seq(owner, key)` → the §B5 token, below.

**Three things that had to be got right, and were only found by looking:**

1. **`el.disabled = true` does nothing on a `<span>`.** Several action "buttons" here are
   `<span class="btn">` with an inline onclick (`triggerDetail.js:53-54`). Assigning `.disabled` to
   a span is silently ignored and the click still fires. The busy state therefore also sets a
   `.is-busy` class whose CSS carries `pointer-events:none` — that class, not `.disabled`, is what
   actually makes those inert.
2. **`JA.utils.confirm` stacks a new overlay per call.** So two quick clicks on Delete open two
   dialogs and confirming both sends two real DELETEs. Element-level disabling is not sufficient
   where the card is re-rendered while the dialog is open, so `deleteJar`, `dashboard.triggerClaude`
   and `_triggerClaudeEnrichment` also carry a per-id in-flight set / flag.
3. **The busy CSS is keyed on `.is-busy` only, never on `[aria-busy]`.** `aria-busy` is legitimate
   on a loading *container*, and `pointer-events:none` on a container would break scrolling inside
   a loading panel.

**A worse defect found while fixing config.js's three delete buttons.** All three did:

```js
await fetch(url, { method: 'DELETE' });   PA.toast('Deleted', 'success');
```

`fetch` only rejects on a **network** failure — a 500 resolves normally. So a delete the server
*refused* reported "Deleted" and re-rendered the list as if it had gone. All three now check
`res.ok`. This is a bigger bug than the missing disabled state it was found behind.

**Measured after:** 16 `UIBusy.begin`/`run` call sites; 66 `.disabled =` toggles (was 50).
Cache-busters bumped on every versioned file touched.

### B5 ☑ Re-audit stale-response guards — 17 genuine races found and fixed

**768 `await`/`.then` sites enumerated** across `jar/js`, `plsql/js` and `parser/js` (the earlier
figure of "~117 in jar/js" was both partial and confined to one UI). ~55 function bodies were read
in full; **17 genuine races fixed, in 14 files.**

**The method was validated against known-truth cases before any of its output was trusted**, because
three scanners in this branch have already produced confidently wrong answers. Required outcomes:
`summary-codeview.js` must come out SAFE (it re-checks `entry.fqn !== fqn`) and `summary-trace.js
_nodeNavGo` must come out already-guarded. Both did — as did four more that were already correct
(`parser/js/callGraph.js _gen`, `parser/js/sourceView.js` **modal**, `parser/js/tableDetail.open`
`_openGen`, `jar/js/codeTree._loadClassMembers`).

#### The trap, encoded in the helper

`UIBusy.seq(owner, key)` exists specifically so the counter cannot be left uninitialised:

> `++undefined` is `NaN`, and `NaN !== NaN`, so an uninitialised token makes the guard reject
> **every** response and the panel never updates at all — a bug strictly worse than the race it was
> written to fix, and one that presents as "the feature does nothing".

`seq` reads the current value defensively (`typeof … === 'number' ? … : 0`) and returns an
`isCurrent()` closure, so no caller has to remember how to compare it. A new gate test
(§E) fails the build on any hand-rolled `++x._fooSeq` that has no numeric initialiser.

#### Four of these are worth naming individually

- **`_ensureSliceLoaded` is the worst.** `jarId`/`version` are read *before* the await. Switch JAR
  mid-flight and the wrong analysis's slice is merged into `_epReports` **and `_loadedSlices` is set
  to true** — so the correct slice is never fetched again and the screen stays wrong until a full
  reload. A stale render that also poisons the cache.
- **`plsql/js/callGraph.js` is a fix applied to one of a duplicated pair.** The parser twin has
  carried `_gen` for exactly this since it was fixed; the PL/SQL copy never got it. The two files
  are otherwise near-identical, which is precisely how the omission survived. `goTo` additionally
  truncated `breadcrumbStack` *before* the await, discarding entries even when the response was
  then thrown away — the truncation now happens only once the response has won.
- **`#code-panel` has two async writers that each guarded only themselves.** `codeTreePanel.show`
  checked its own `_currentFqn`; `codeTree._openBundledContent` had no guard. Neither could see the
  other, so a bundled-file response could land on top of a class already rendered. Invalidation is
  now **mutual**: `show` bumps the bundled token, `_openBundledContent` clears `_currentFqn`.
- **`parser/js/triggerDetail.js` was a duplicate-DOM-id bug, not a plain race.** `close()` defers

## E. Defect sweep — found outside B4/B5

### E1 ☑ The B1 `trueCount` fix was a no-op. `externalScopeCalls` was still reporting the cap

**This is the headline finding of the sweep, and it is a regression in a fix this file already
records as done.** §B1 says `externalScopeCalls` went from 3,105 to 5,959. On the code as it stood,
it did not.

`JA.utils.trueCount(owner, field)` reads `owner[field + 'Total']`. Both call sites pass a **report
object**, not the endpoint payload — and the report is built by copying selected fields out of the
endpoint:

```js
r.externalCalls = (ep.externalCalls || []).map(e => ({ … }));   // arrays copied
                                                                 // externalCallsTotal NOT copied
r.externalScopeCalls = JA.utils.trueCount(r, 'externalCalls') + …
```

`r.externalCallsTotal` is `undefined`, so `trueCount` fell straight through to `.length` — **the
cap** — on every call. The same is true of `summary-analyzer.js`, which rebuilds every endpoint into
a fresh report object and likewise carried the arrays but not their totals. The helper was correct;
nothing ever gave it anything to read.

**Fixed at the cause**, not by patching the two counts: `JA.utils.carryTotals(dst, src)` copies every
`<field>Total` the server actually emitted, and is called at both report-building sites. Only
present-and-numeric totals are copied, so an untruncated response gains no fields and behaviour is
byte-identical.

**Verified numerically against the real artifact** (`data/jar/unified-web-1.0.0-SNAPSHOT/analysis.json`,
317 endpoints), by emulating the provider's capping and then running the real helper from `utils.js`:

```
externalScopeCalls total   before carryTotals = 3105   after = 5959
```

which is the number §B1 claimed and never achieved.

**Related finding: there are SEVEN capped fields, not four.** `CAPPED_ARRAY_FIELDS` is
`beans` 100 · `externalCalls` 100 · `httpCalls` 50 · `dynamicFlows` 200 · `aggregationFlows` 200 ·
`dynamicCollectionFlows` 200 · `collectionLifecycleFlows` 100. Measured on this machine's analysis,
only `externalCalls` is currently truncated (23 endpoints, 5,958 true vs 3,104 sent); the other six
are under their caps *on this data* and would fail silently the moment they were not.

**One place `trueCount` genuinely cannot help, and pretending otherwise was itself the bug.**
`summary-vertical.js` called `trueCount(report, 'beans')` on `report.beans` — a **locally built,
de-duplicated aggregate**, not a server array. There is no `beansTotal` and there never can be. The
call read as a truncation fix while doing nothing. It is now honest `.length`, and the header states
the real caveat: the aggregate is derived from capped `externalCalls`, so it prints
`⚠ lower bound — 3,104 of 5,958 cross-module calls available` whenever any source endpoint was
truncated.

### B15 ☑ A count comparison marked a correctness fix as a regression

Comparing the post-agent run against the B14 baseline showed **ORACLE 30 → 19** tables with column
detail, and I called it a regression. It is not — the count fell because **wrong data was removed**.

History from the artifacts, which is what settled it:

```
02:48  withCols=30   <- baseline
03:42  withCols=19   <- after the agent added ownedBy()
03:47  withCols=19   <- after my cache-version fix (no effect; cache was not the cause)
```

All **11** tables that lost detail have `operations: ["SELECT"]` — read-only — and had been given
**`SET`** usages. For `INSERT INTO audit SELECT ... FROM orders`, the statement yields both INSERT
usages (audit's columns) and SELECT usages (orders' columns), and every one of them was being
attached to whichever table operation was being enriched. So a read-only table's page asserted that
its columns were *written*. `ownedBy()` keeps only the usages belonging to that operation's own
table.

**The lesson, and it applies to the whole branch:** a raw count comparison cannot tell an
improvement from a regression. Fewer rows can mean less wrong data. The baseline is still worth
having — it is what made the change visible at all — but a fall in a count is a prompt to look, not
a verdict.

I also fixed a genuine defect while chasing the wrong hypothesis, and it is worth keeping:
`NodeParseCache`'s key was `md5(visitKey + sourceText)` with **no parser version**, so identical
source always hit a stale cache however much the analyser had changed — an extraction improvement
could never reach an already-cached node. The key now includes `PARSE_SCHEMA_VERSION`.

### B17 ☑ The DDL question answered — and it uncovered silent data loss

`ddl[]` was 0 in all five dialects and I had assumed the demo schemas simply contain no
in-procedure DDL. **Wrong, and the truth is worse.**

Seeded a real MySQL procedure containing `TRUNCATE TABLE`, analysed it, and compared against the
identical procedure with that one line removed:

```
ERP_USP_DDL_PROBE     (TRUNCATE + INSERT + UPDATE)   0 tables, 0 operations
ERP_USP_NODDL_PROBE   (INSERT + UPDATE only)         1 table,  [INSERT, UPDATE]
```

**`TRUNCATE TABLE` was absent from `routineStatement` in the MySQL grammar, so no alternative
matched, the enclosing body failed, and the entire procedure yielded nothing — not even its
INSERTs.** Nothing failed loudly: the node came back with `statementSummary: {}` and three lines of
code. Any MySQL procedure containing a TRUNCATE has been contributing *nothing* to the analysis,
and no dialect has ever recorded a TRUNCATE operation.

Fixed across the stack: `TRUNCATE` lexer token, a `truncateStatement` rule (with the `TABLE`
keyword optional, as MySQL allows), a `DmlType.TRUNCATE`, and `visitStmtTruncate` recording it with
its SQL text so the shared enricher can work on it. Verified end to end on a real analysis:

```
column coverage [ERP_USP_DDL_PROBE] 1/1 tables (100.0%), 2 column rows, 1 DDL rows
ANALYZERDB.ERP_DDL_PROBE_TARGET  ops=[TRUNCATE, INSERT, UPDATE]  ddl=1  cols=2
    DDL: action=TRUNCATE object=ERP_DDL_PROBE_TARGET type=TABLE line=3
    col: NOTE usages=[INSERT, SET] sources=[LITERAL]
```

`TruncateDoesNotKillBodyTest` (4 tests) pins it. **The first test is the one that matters** — it
asserts the statements *around* a TRUNCATE survive, because that is the property that was lost and
the one that breaks again if another statement type goes missing. Probe procedure, probe table and
probe analysis directories all removed afterwards.

**Open, and worth its own task:** this was found by chance while proving a feature. The same hole
exists for any statement type absent from any of the five grammars, and the failure is silent. A
gate that parses each dialect's real sources and fails on a body that yields zero statements would
catch the class, not just this instance.
