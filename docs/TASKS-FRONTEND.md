## How to read a task

Each task has:

- a stable **ID** (`FE-001`…) that is never reused or renumbered;
- the **finding IDs** it resolves;
- the **files** it touches;
- **blocked-by** dependencies, by ID;
- a **definition of done** that is a command to run or an observable result — never an opinion;
- the **test that proves it**.

## Testing convention

The repo convention is that **a gate test is calibrated by deliberately breaking it**: after writing the
test, revert the fix (or introduce the failure the test is meant to catch), confirm the test goes red, then
restore the fix and confirm it goes green. A test that has never been observed to fail is treated as
worthless and does not satisfy a definition of done.

This matters more than usual here because the audit measured **zero existing frontend tests** — no
`package.json` exists anywhere in the repo, and `unified-web/src/test` contains only `java`. `FE-001`
therefore blocks nearly everything else: until there is a harness, no task can be proven done.
